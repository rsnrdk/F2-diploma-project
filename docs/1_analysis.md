# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ

## 1.2 Аналіз існуючих аналогів

Для аналізу обрано три програмні системи, що розв'язують задачу отримання криптографічно верифікованих випадкових значень: Chainlink VRF (блокчейн-оракул), drand (розподілений маяк випадковості) та RANDOM.ORG Signed API (централізований сервіс із підписаними відповідями). Системи розглянуто виключно як інженерні рішення: за архітектурним патерном, протоколами взаємодії, стеком даних, криптографічним механізмом та відомими технічними обмеженнями (Technical Bottlenecks).

### 1.2.1 Chainlink VRF

**Архітектурний патерн.** Гібридна подієво-керована архітектура, що складається з on-chain компонента (смарт-контракт `VRFCoordinator` у мережі EVM-сумісного блокчейну) та off-chain мережі вузлів-оракулів (Chainlink node, Go). Контракт-споживач викликає метод `requestRandomWords`, координатор генерує подію (event log), вузол-оракул фіксує подію, обчислює результат і надсилає транзакцію `fulfillRandomWords`. Масштабованість системи обмежена пропускною здатністю базового блокчейну та вартістю газу, а не обчислювальною потужністю вузлів.

**Протоколи взаємодії.** Взаємодія вузла з блокчейном здійснюється через Ethereum JSON-RPC (HTTP/WebSocket) із підпискою на event logs. Взаємодія вузла з контрактом здійснюється виключно транзакціями. REST або gRPC API для зовнішніх систем не передбачено: споживачем результату може бути лише смарт-контракт.

**Криптографічний механізм.** Застосовано ECVRF (Verifiable Random Function на еліптичній кривій secp256k1). Вхідними даними є ключ оракула та seed, сформований з параметрів запиту й хешу блоку. Вихідними даними є випадкове значення та криптографічний доказ (proof), який перевіряється контрактом-координатором on-chain до передачі результату споживачу.

**Стек даних і консистентність.** Джерелом істини є стан блокчейну; консистентність забезпечується консенсусом мережі. Захист від реорганізації ланцюга (reorg) досягається параметром `requestConfirmations` — очікуванням заданої кількості блоків перед обробкою запиту. Внутрішній стан вузла-оракула зберігається у PostgreSQL.

**Technical Bottlenecks:**

- Latency отримання результату становить щонайменше N підтверджень блоків та час включення транзакції відповіді (від секунд до хвилин залежно від мережі).
- Кожен запит потребує оплати газу callback-транзакції та комісії оракула; вартість зростає лінійно з частотою запитів.
- Сервіс недоступний для систем, що функціонують поза блокчейн-середовищем.
- Оракул не здатен спотворити результат, проте здатен не надати відповідь (проблема liveness).
- Параметри ймовірнісної моделі (правила інтерпретації випадкового значення) реалізуються в коді контракту-споживача; у разі використання upgradeable-контрактів (proxy pattern) ці параметри можуть бути змінені, і механізм VRF такої зміни не фіксує.

### 1.2.2 drand (League of Entropy)

**Архітектурний патерн.** Децентралізований маяк випадковості (randomness beacon): мережа незалежних вузлів (Go), що перебувають під керуванням різних організацій. Вузли спільно формують випадкове значення з фіксованим інтервалом (раунд) за пороговою схемою t-з-n. Масштабування операцій читання забезпечується мережею relay-вузлів; генерація не масштабується, оскільки раунди формуються строго періодично.

**Протоколи взаємодії.** Взаємодія між вузлами здійснюється через gRPC. Публічний доступ надається через HTTP JSON API relay-вузлів, а також через розповсюдження в мережі libp2p gossipsub.

**Криптографічний механізм.** Застосовано порогові підписи BLS (крива BLS12-381) із розподіленою генерацією ключа (DKG). Значення раунду обчислюється як `SHA256(signature)` і перевіряється одним груповим публічним ключем. У режимі chained кожен раунд містить підпис попереднього; у режимі unchained (мережа quicknet, інтервал 3 с) раунди незалежні.

**Стек даних і консистентність.** Кожен вузол зберігає ланцюг раундів у вбудованому key-value сховищі (BoltDB); у новіших версіях передбачено бекенд PostgreSQL. Консистентність випливає з детермінованості порогового підпису: для заданого раунду існує єдине валідне значення незалежно від того, які t вузлів його сформували.

**Technical Bottlenecks:**

- Значення кожного раунду одночасно стає доступним усім учасникам мережі; для формування персоналізованого прихованого результату воно непридатне без додаткової схеми комітменту на майбутній раунд.
- Значення доступне лише один раз за період (3 с або 30 с); генерація за запитом (on-demand) не підтримується.
- Вхідні дані клієнта (аналог `client_seed`) не передбачені; результат не залежить від споживача.
- За недоступності менше ніж t вузлів формування раундів зупиняється.
- Механізм фіксації параметрів ймовірнісної моделі та підпису результату інтерпретації не передбачено.

### 1.2.3 RANDOM.ORG Signed API

**Архітектурний патерн.** Централізований сервіс одного оператора (Randomness and Integrity Services Ltd.). Джерелом ентропії є апаратний генератор істинно випадкових чисел (true RNG) на основі атмосферного шуму. Внутрішня архітектура публічно не розкривається, що унеможливлює незалежний аудит реалізації.

**Протоколи взаємодії.** JSON-RPC 2.0 поверх HTTPS (API Release 4). Окремий набір методів Signed API (`generateSignedIntegers` та інші) повертає результат разом із цифровим підписом; перевірка підпису виконується методом `verifySignature`.

**Криптографічний механізм.** Відповідь підписується алгоритмом RSA із хешуванням SHA-512. Кожна підписана відповідь містить поле `serialNumber`, що монотонно зростає в межах API-ключа і дозволяє виявити пропущені результати.

**Стек даних і консистентність.** СУБД та механізми забезпечення консистентності публічно не документовано. Зберігання історії операцій реалізовано в окремому сервісі Third-Party Draw Service.

**Technical Bottlenecks:**

- Результат true RNG неможливо незалежно відтворити; перевірка обмежується автентичністю підпису (походженням результату), а не коректністю обчислення.
- Схема commit-reveal відсутня, тому неможливо довести, що значення не було обране оператором серед кількох згенерованих.
- Встановлено добові квоти на кількість бітів і запитів у межах API-ключа.
- Latency визначається зовнішнім HTTPS-викликом до єдиного оператора; резервування на боці клієнта не передбачено.
- Механізм фіксації параметрів ймовірнісної моделі не передбачено.

### 1.2.5 Аналітичний висновок підрозділу

Проведений аналіз показав, що кожна з розглянутих систем розв'язує лише частину задачі верифікації випадкового процесу. Chainlink VRF забезпечує криптографічний доказ коректності кожного окремого результату, проте прив'язаний до блокчейн-середовища, що зумовлює latency на рівні підтверджень блоків, лінійне зростання вартості операцій та неможливість інтеграції із системами поза блокчейном. drand усуває залежність від одного оператора завдяки пороговій схемі BLS, однак формує лише публічні значення з фіксованим інтервалом, без генерації за запитом і без урахування вхідних даних клієнта. RANDOM.ORG Signed API надає синхронний програмний інтерфейс із підписаними відповідями, але через невідтворюваність true RNG та відсутність схеми commit-reveal перевірка обмежується автентичністю походження результату і вимагає повної довіри до оператора. Спільним обмеженням усіх трьох систем є відсутність механізму фіксації параметрів ймовірнісної моделі: навіть за коректно згенерованого випадкового значення правила його інтерпретації залишаються поза межами верифікації.

У межах кваліфікаційної роботи запозичено такі архітектурні рішення аналогів: криптографічний доказ для кожного окремого результату (Chainlink VRF), відкриту перевірку одним публічним ключем (drand) та монотонний лічильник операцій для виявлення пропущених результатів (`serialNumber` у RANDOM.ORG), що реалізується як перевірка безперервності nonce. Водночас уникнуто прив'язки до блокчейн-середовища, періодичної генерації без участі клієнта та невідтворюваного джерела ентропії. Обраний стек забезпечує синхронну обробку запиту через REST API: детермінований результат обчислюється за схемою HMAC-SHA256 із commit-reveal, що дозволяє незалежно відтворити його після розкриття seed; підпис Ed25519 виконується всередині HashiCorp Vault без вивантаження приватного ключа; атомарність операцій та ідемпотентність запитів забезпечуються транзакціями PostgreSQL. Подвійний комітмент — seed окремо від параметрів ймовірнісної моделі — закриває клас маніпуляцій, не адресований жодним із розглянутих аналогів.

Архітектурний компроміс (trade-off) проєктованої системи полягає в централізованості оператора: на відміну від drand, доступність сервісу залежить від однієї інфраструктури. Цей компроміс прийнято свідомо, оскільки модель довіри не вимагає довіри до оператора щодо чесності результату — її забезпечують комітменти та підписи, — а ризик недоступності мінімізується горизонтальним масштабуванням stateless-реплік, реплікацією даних і визначеною політикою деградації. Перехід до порогової схеми розподілу секрету між кількома сторонами розглядається як напрям подальшого розвитку. Визначені вимоги до архітектури, моделі даних та механізмів відмовостійкості є вхідними даними для проєктування системи, викладеного в Розділі 2.
