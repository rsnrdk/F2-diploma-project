# ADR-001: Вибір сховища ключів і виконавця криптографічних операцій

**Статус:** Approved
**Дата:** 2026-11-19
**Автор:** Редько Арсеній
**Пов'язані вимоги:** [SRS-FUN-01](../srs.md#srs-fun-01), [SRS-FUN-02](../srs.md#srs-fun-02), [SRS-FUN-09](../srs.md#srs-fun-09), [SRS-FUN-13](../srs.md#srs-fun-13), [SRS-NFR-SEC-04](../srs.md#srs-nfr-sec-04), [SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01), [SRS-NFR-REL-01](../srs.md#srs-nfr-rel-01)
**Архітектура:** контейнер Vault і компонент VaultTransitAdapter ([2_design.md](../2_design.md#diagram-level2))

---

## Context

Модель довіри ProvaTrace ґрунтується на трьох типах ключового матеріалу:

- кореневий ключ Ed25519 (1 на сервіс) – підписує сертифікати ключів систем-інтеграторів;
- ключі підпису Ed25519 (по одному на систему-інтегратора, з ротацією) – підписують кожну операцію, конфігурації моделей і `RevealRecord`;
- симетричний ключ AES-256-GCM – шифрує `server_seed` до моменту розкриття.

Обмеження, що накладає SRS:

1. Приватний ключ не повинен існувати поза захищеною межею, зокрема в пам'яті процесу Core API ([SRS-NFR-SEC-04](../srs.md#srs-nfr-sec-04)).
2. Core API, що обробляє публічний трафік, не повинен мати доступу до кореневого ключа.
3. Кожна операція `roll()` виконує два криптографічні виклики (розшифрування seed і підпис) і повинна вкладатися в p95 ≤ 150 мс при 200 RPS ([SRS-NFR-PERF-01](../srs.md#srs-nfr-perf-01)), тобто до 400 криптографічних операцій на секунду.
4. Демонстраційне середовище – один хост із Docker Compose без хмарного облікового запису; рішення має розгортатися локально.
5. Кожна операція з ключем повинна фіксуватися в незалежному журналі для звірки з реєстром.

## Alternatives

### A. Ключі в застосунку (Node.js `crypto`, ключі в змінних середовища або в БД)

- Нульова мережева затримка: підпис Ed25519 у процесі – десятки мікросекунд.
- Приватний ключ перебуває в пам'яті кожної репліки Core API: дамп пам'яті, витік змінних середовища чи резервної копії БД розкриває ключ. Порушує обмеження 1.
- Неможливо розмежувати доступ до кореневого ключа і ключів інтеграторів на рівні політик; розмежування лише організаційне. Порушує обмеження 2.
- Аудит операцій з ключами реалізується власним кодом, що контролює той самий процес. Порушує обмеження 5.

### B. Хмарний KMS (AWS KMS / Google Cloud KMS)

- Ключі в керованих HSM (FIPS 140-2/3), неекспортовані; IAM-політики та аудит (CloudTrail / Cloud Audit Logs) з коробки.
- Вартість лінійно залежить від кількості операцій: при цільовому навантаженні 400 операцій/с обсяг перевищує 10^10 викликів на рік, що робить кожен виклик статтею витрат (FinOps).
- Мережева затримка до регіонального ендпоінта KMS – одиниці-десятки мілісекунд на виклик; два виклики на `roll()` споживають значну частину бюджету p95.
- Квоти на кількість запитів на секунду до ключа потребують узгодження з провайдером.
- Vendor lock-in: API, IAM і формат ключів прив'язані до провайдера; локальне розгортання без хмарного облікового запису неможливе. Порушує обмеження 4.

### C. HashiCorp Vault, Transit Secrets Engine (self-hosted)

- Ключі Ed25519 і AES-256-GCM створюються всередині Vault з `exportable = false`; застосунок отримує лише результат операції.
- Політики доступу за шляхами: Core API – `sign` ключами інтеграторів, `encrypt` / `decrypt` seed; Onboarding Service – операції з кореневим ключем.
- Вбудований аудит-лог кожної операції.
- Розгортання в тій самій мережі, що й Core API; ліцензійних витрат на операцію немає.
- Програмне сховище ключів, а не апаратний HSM; захист ключів залежить від захисту хоста Vault і процедури розпечатування.

### D. Апаратний HSM (локальний або HSM-as-a-Service)

Відкинуто без детального порівняння: вартість обладнання чи сервісу та складність експлуатації непропорційні масштабу MVP. Розглядається як заміна сховища на етапі промислової експлуатації.

## Decision

Обрано **альтернативу C – HashiCorp Vault (Transit Secrets Engine)** з кластером Integrated Storage (Raft) з трьох вузлів у цільовому розгортанні та одним вузлом у демонстраційному.

Обґрунтування за обмеженнями:

| Обмеження | A. У застосунку | B. Хмарний KMS | C. Vault Transit |
|---|---|---|---|
| 1. Ключ поза процесом Core API | ✗ | ✓ | ✓ |
| 2. Розмежування доступу до root-ключа | ✗ | ✓ | ✓ |
| 3. Затримка 2 викликів у бюджеті p95 ≤ 150 мс | ✓ | частково (мережа до регіону) | ✓ (локальна мережа, одиниці мс) |
| 4. Локальне розгортання без хмари | ✓ | ✗ | ✓ |
| 5. Незалежний аудит операцій | ✗ | ✓ | ✓ |
| Вартість на операцію | 0 | лінійна | 0 (інфраструктура хоста) |

Альтернатива C – єдина, що задовольняє всі п'ять обмежень SRS. Залежність бізнес-логіки від Vault ізольовано інтерфейсами `SigningPort` і `SeedCipherPort` ([2_design.md](../2_design.md#diagram-level3)), тому перехід на апаратний HSM чи хмарний KMS не потребує змін у доменному ядрі.

## Consequences

**Позитивні:**

- Приватні ключі не потрапляють у пам'ять, логи, дампи чи резервні копії Core API.
- Компрометація Core API не дає змоги сертифікувати сторонній ключ: політика root-ключа належить лише Onboarding Service.
- Аудит-лог Vault дозволяє звіряти кількість підписів із кількістю записів у реєстрі.
- Публічна верифікація не залежить від Vault: перевірка виконується публічними ключами з БД ([SRS-NFR-REL-05](../srs.md#srs-nfr-rel-05)).

**Негативні та ризики:**

- **Додаткова мережева затримка:** два синхронні виклики Vault на кожну операцію `roll()`; при деградації мережі чи Vault зростає p99. Пом'якшення: таймаут 2 с, ROLLBACK без зміни стану ([SRS-NFR-REL-03](../srs.md#srs-nfr-rel-03)).
- **Нова точка відмови на критичному шляху:** недоступність Vault зупиняє generate / roll / reveal. Пом'якшення: кластер Raft з 3 вузлів, auto-unseal, моніторинг лідера.
- **Операційна складність:** процедура розпечатування (схема Шаміра або auto-unseal), ротація секретів AppRole, оновлення версій, резервні знімки Raft. Втрата Vault разом із копіями робить нерозкриті seed-пари нерозшифровуваними.
- **Ускладнення CI/CD:** інтеграційні тести потребують контейнера Vault (Testcontainers), а пайплайн – безпечної доставки `role_id` / `secret_id`.
- **Ліцензійний ризик:** Vault поширюється під Business Source License 1.1. Використання в ProvaTrace дозволене, оскільки сервіс не є конкурентним продуктом керування секретами; резервний варіант – сумісний форк OpenBao (MPL 2.0) з тим самим API.
- **Відсутність апаратної ізоляції:** рівень захисту ключів нижчий, ніж у FIPS 140-3 HSM; для промислової експлуатації передбачено перехід на HSM через ті самі порти.
- **FinOps:** ліцензійних витрат на операцію немає, але з'являються витрати на 3 додаткові вузли кластера Vault та їх супровід.
